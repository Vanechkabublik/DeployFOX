# Восстановление после потери VPS

**Условие:** у вас есть исходники совместимой версии, управляющий dump, .env с ENCRYPTION_KEY, GitHub PEM, данные пользовательских баз/volumes и сведения о доменах. Без копий данных их нельзя восстановить из карточек панели. Не меняйте DNS рабочего сервера для пробного восстановления.

1. Купите отдельный VPS Ubuntu 24.04.
2. Пройдите SSH, безопасность, Docker по главам 02–04.
3. Перенесите исходники и копию в закрытую папку.
4. Проверьте контрольные суммы: `cd КАТАЛОГ_КОПИИ && sha256sum -c SHA256SUMS`.
5. Разместите оригинальный config.env как `.env`, PEM как `secrets/github-app.pem`. Сохраните права по главе GitHub. Не генерируйте новый ключ шифрования поверх старого.
6. Не запускайте старые domain routes на тестовом VPS без адаптации. Для базы достаточно:

```bash
sudo docker compose -f docker-compose.prod.yml up -d postgres redis
```

7. Из папки DeployFox выполните:

```bash
sudo bash infrastructure/scripts/restore.sh /ПОЛНЫЙ/ПУТЬ/К/КОПИИ
```

Скрипт проверит суммы, остановит API/worker/frontend, запросит RESTORE и заменит управляющую базу через pg_restore --clean --if-exists. При ошибке службы остаются остановленными. Он **не** копирует .env автоматически и **не** восстанавливает управляемые базы, приложения, routes или volumes.

8. Отдельно восстановите пользовательские базы из их проверенных logical dump. Смена IP не меняет Docker volume автоматически; идентификаторы и hostname должны быть согласованы с переменными приложения. Поскольку автоматическая процедура ещё не реализована, потренируйтесь на копии с человеком, знакомым с PostgreSQL/MySQL, прежде чем доверять единственные важные данные этой версии.
9. Создайте/проверьте BuildKit builder через install.sh без изменения .env. Проверьте контейнеры, переменные, логи, повторно разверните совместимые проекты.
10. Проверьте вход старым паролем, расшифровку env через успешный запуск приложения, чтение/запись данных и основные пользовательские действия.
11. Только после успешной проверки переключите A-записи на новый IP. Дождитесь TTL, проверьте сертификаты и webhook deliveries.
12. Сделайте новую offsite-копию восстановленного состояния.

Протокол успешного восстановления должен содержать дату, версии, количество восстановленных данных и фактические проверки приложения. До такого опыта нельзя утверждать, что backup/restore полностью работает. Проверка `pg_restore --list` сама по себе не является restore-тестом.
