# Что происходит после git push

Для проекта включите Auto deploy при создании. GitHub App должна быть установлена на этот репозиторий, а выбранная ветка должна совпадать с веткой push.

В локальной папке вашего приложения:

```bash
git status
git add .
git commit -m "Update application"
git push
```

Не запускайте `git add .`, если в папке есть незащищённые секреты: сначала проверьте .gitignore и git status.

1. GitHub принимает commit.
2. Отправляет подписанный webhook на панель.
3. API проверяет HMAC SHA-256, delivery ID, URL репозитория и имя ветки.
4. PostgreSQL сохраняет задачу, Redis будит worker.
5. Worker получает глобальную блокировку: на VPS выполняется одна тяжёлая сборка.
6. Agent клонирует репозиторий и получает указанный webhook commit. Собирается образ с уникальным тегом.
7. Создаётся кандидат, проверяется HTTP healthcheck.
8. Для проекта с доменом агент записывает маршрут, проверяет Caddy validate и делает reload.
9. Только после успеха старый контейнер останавливается.
10. В истории появляется SUCCESS или FAILED.

В панели откройте Деплои → Логи. Agent передаёт строки Docker pull/build и подготовки Railpack во время выполнения, worker сохраняет их, а SSE доставляет в браузер. Вывод ограничен 1 MiB на попытку и 4 KiB на строку; лишнее отбрасывается. Операции Git с учётными данными не транслируются. Поведение проверено тестом получения строки до завершения процесса и тестами протокола agent/worker; внешняя GitHub-сборка требует отдельной проверки.

Если push пришёл во время активного деплоя, уникальный индекс защищает от конфликта, а последний commit сохраняется как pending. После завершения текущей задачи он ставится в очередь. Несколько быстрых push объединяются в последний commit: каждый промежуточный push не обязательно становится отдельным релизом.

При временных сетевых ошибках сборки worker делает до трёх попыток с задержками 1 и 2 секунды. Между попытками проверяется отмена. Переключение трафика автоматически не повторяется: такой повтор может изменить уже работающее приложение.

При рестарте worker задачи QUEUED сохраняются; прерванные активные операции помечаются FAILED с указанием проверить Docker/Caddy. Автоматическое восстановление состояния уже переключённого контейнера пока не реализовано.
